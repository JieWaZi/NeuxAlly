# 插件 v2 Spec：标准映射、原生交付与验收

> 状态：待评审。本文规定目标行为，不表示当前实现已通过这些要求。
> 意图、当前代码与职责见 [插件 v2 设计](2026-10-19-plugin-v2-design.md)。本文不是新的插件文件格式或 JSON Schema。

## 1. 采用的官方规范

规范依据核对日期为 2026-10-19。下列官方文档可能继续更新，adapter 实施时需同时记录实际 CLI 版本与支持的语义。

| 范围           | 权威来源                                                                                                           | 本系统采用方式                                      |
| -------------- | ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------- |
| 通用清单       | [Agent Plugins 1.0.0 Schema](https://agent-plugins.org/schemas/1.0.0/plugin.schema.json)                           | 自有通用包直接采用，不新增必填顶层字段              |
| 通用 MCP       | [MCP Schema](https://agent-plugins.org/schemas/1.0.0/mcp.schema.json)                                              | 按传输和字段语义转换，不只修改文件名                |
| OpenAI 打包    | [Package your plugin](https://developers.openai.com/plugins/build/plugins)                                         | 通用根清单及 `com.openai` 扩展；接受兼容布局        |
| Codex 原生安装 | [CLI 插件命令](https://learn.chatgpt.com/docs/developer-commands?surface=cli)                                      | 按实际版本使用原生安装、列表与 marketplace 管理结果 |
| CC 清单        | [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)                                     | 保留字段、默认发现及替换或合并语义                  |
| CC 组件        | [Plugin components](https://code.claude.com/docs/en/plugins/components)                                            | 原生组件由 CC 执行，不实现第二套解释器              |
| CC marketplace | [Create a marketplace](https://code.claude.com/docs/en/plugin-marketplaces)                                        | 使用官方目录格式和来源定位                          |
| CC 安装与加载  | [Plugin commands](https://code.claude.com/docs/en/plugins/cli-reference)                                           | 原生安装或会话目录加载，准确登记作用域              |
| 实际 OpenAI 包 | [openai/plugins 固定提交](https://github.com/openai/plugins/tree/0722921d5542fc593105c27bd52630babd8b8c2a/plugins) | 作为第三方来源和兼容样例，逐包保留声明              |

通用清单的 Schema 要求 `$schema` 与 `name`，其余标准属性包括 `version`、`description`、`author`、`homepage`、`repository`、`license`、`keywords` 和 `extensions`。根级别不添加 `allyPluginVersion`、自定义组件列表或新的格式标识。`extensions` 使用规范允许的命名空间，原生清单仍遵循各自规范。

## 2. 标准目录与识别

| 内容     | 通用 Agent Plugins                 | Codex 兼容包                                  | Claude Code 原生包                           |
| -------- | ---------------------------------- | --------------------------------------------- | -------------------------------------------- |
| 主清单   | 根 `plugin.json`                   | `.codex-plugin/plugin.json`                   | `.claude-plugin/plugin.json`                 |
| 技能     | 根 `skills/`                       | 默认 `skills/` 及原生声明                     | 默认 `skills/` 及原生声明                    |
| MCP      | 根 `mcp.json`                      | 默认 `.mcp.json` 及原生声明                   | 默认 `.mcp.json` 及原生声明                  |
| 平台配置 | `extensions.com.openai` 等命名空间 | 兼容清单与配套文件                            | CC 清单与配套文件                            |
| 说明     | 插件根 README                      | 插件根 README                                 | 插件根 README                                |
| 其他组件 | 按扩展声明保留                     | 保留 apps、hooks、agents、commands 等实际内容 | 保留 hooks、agents、commands、LSP 等实际内容 |

目录与包文件必须保持完整相对结构，不只复制 `SKILL.md`。发布包不含 Git 工作目录，但包含脚本、引用资料、资产和必要可执行文件的执行位。

根通用清单存在时，它是通用身份和标准组件依据；目标平台配置分别读取。`extensions.com.openai` 为对象时，整体优先于 Codex 兼容 overlay，不对两个对象逐字段补齐。没有该对象时才采用兼容 overlay。只有原生清单时直接按原生格式导入，不先生成通用清单。

同时存在两个原生清单且没有根通用清单时，显式来源格式决定本次导入视图；来源没有指定时先选择本次目标 CLI 的清单，仍不能确定时要求选择格式。完整包只保存一份，两个原生清单都保留，不拼接成一份混合清单。

CC 的默认目录合并规则不能统一处理成“所有目录相加”。以当前官方清单为准：`skills` 追加默认发现；`commands`、`agents`、`outputStyles` 等声明可替换默认发现；hooks 和 MCP 等具有各自合并与覆盖规则。parser 与转换测试需要覆盖这些差异。CC 允许无清单的标准组件目录由原生机制识别；通过该机制发现的包可登记，但无法推导的元数据保持缺省，不伪造清单或版本。

### 2.1 标准包示例

以下仅用虚构插件展示官方格式的组合，不定义新的包格式。`skills/issue-review/SKILL.md` 及其资源直接采用技能目录约定；根清单不重复声明通用技能路径。

根 `plugin.json`：

```json
{
  "$schema": "https://agent-plugins.org/schemas/1.0.0/plugin.schema.json",
  "name": "issue-helper",
  "version": "1.0.0",
  "description": "检索问题并辅助整理处理建议"
}
```

根 `mcp.json`：

```json
{
  "$schema": "https://agent-plugins.org/schemas/1.0.0/mcp.schema.json",
  "mcpServers": {
    "issues": {
      "type": "streamable-http",
      "url": "https://example.com/mcp"
    }
  }
}
```

生成 CC 清单时可以在 `.claude-plugin/plugin.json` 中使用同一身份元数据及 `"mcpServers": "./.mcp.json"`，把 `.mcp.json` 中该服务的传输值转为目标使用的 `http`。生成 Codex 兼容清单时使用 `.codex-plugin/plugin.json`，技能与 MCP 的原生字段由对应 adapter 声明。根 README、技能正文及不需要改写的其他文件保持原样。

## 3. 用于软件展示的标准字段

下表的 OpenAI `interface` 表示选定的 `extensions.com.openai.interface`，或符合上一节优先级的兼容清单 `interface`。CC 字段依据其原生清单；仅服务目录展示的字段，不因此成为运行依赖。

| 系统展示       | 通用 / OpenAI 字段                               | CC 字段或来源                        | 展示规则                                                  |
| -------------- | ------------------------------------------------ | ------------------------------------ | --------------------------------------------------------- |
| 标题           | `interface.displayName`，回退 `name`             | `displayName`，回退 `name`           | 用户明确设置的本机展示别名优先；保留原始名称              |
| 列表简介       | `interface.shortDescription`，回退 `description` | `description`                        | 展示原文，不由模型改写成新的权威说明                      |
| 说明正文       | 根 `README.md`，兼容 `readme.md`                 | 相同                                 | README 优先；缺失才回退 `longDescription` / `description` |
| 完整说明弹窗   | 同一来源版本 README                              | 相同                                 | 显示完整 Markdown，不把长描述冒充 README                  |
| 作者           | `author.name/url/email`                          | `author.name/url/email`              | 保留实际作者，不用收录方覆盖                              |
| 展示开发者     | `interface.developerName`，回退作者              | 作者；原生目录可提供展示资料         | 与第三方作者、适配维护者可分别表达                        |
| 版本           | `version`                                        | `version`                            | 目标实现显示自己的实际版本；缺失时明确采用内容摘要标识    |
| 仓库           | `repository`                                     | `repository`                         | 这是作者声明，实际下载来源由回执另列                      |
| 官网           | `interface.websiteURL`，回退 `homepage`          | `homepage`                           | 仅合法 HTTP/HTTPS 链接                                    |
| 文档入口       | README 及清单公开链接                            | `documentationUrl`、README           | 不作为清单解析或安装指令来源                              |
| 许可           | `license` 与随包许可文件                         | 相同                                 | 逐包保留，不替换为主应用许可                              |
| 分类           | `interface.category` 或原生目录分类              | 原生目录分类                         | 无值时不推断新的分类                                      |
| 标签           | `keywords`                                       | `keywords`                           | 缺失保持为空                                              |
| 图标           | `interface.logo` / `composerIcon`                | `icon` 或目录资产                    | 按主题选择可用资产，沿用受管资产校验；失败回退默认图标    |
| 暗色图标       | 兼容包中实际声明的 `logoDark` 等展示扩展         | 原生目录资产                         | 字段存在时读取，保留其来源，不宣称所有格式均必填          |
| 截图与品牌色   | `interface.screenshots/brandColor`               | 原生目录展示资料                     | 可选资料；是否展示由当前页面需要决定                      |
| 隐私与条款     | `interface.privacyPolicyURL/termsOfServiceURL`   | `privacyPolicyUrl/termsOfServiceUrl` | 原生键的大小写分别解释                                    |
| 建议提示       | `interface.defaultPrompt`                        | 原生目录提供时读取                   | 仅用户主动选择后形成输入，不自动执行                      |
| 能力           | 实际 skills、MCP 与完整原生组件索引              | 相同                                 | 展示真实组成，不以 `interface.capabilities` 代替组件事实  |
| 所需配置       | 原生配置声明与现有授权绑定                       | `userConfig` 等                      | 敏感值不回显；声明不等于已配置                            |
| 来源及安装状态 | 来源解析与原生安装回执                           | 相同                                 | 不能从 README、“已下载”或仓库 URL 推断已安装              |

包中未知字段和展示扩展完整保留，但不自动变成系统开关、权限或命令。共享配置及伙伴关系不写回第三方清单。

## 4. 目标原生来源关联

### 4.1 这是业务关联，不是新插件标准

OpenAI 和 CC 没有共同定义“另一个生态中的对应插件”字段。该信息必须清楚标注为 NeuxAlly 维护的业务关联，不能包装成官方通用字段。

自有通用包可在现有 `extensions.com.ally.nativePlugins` 中携带关联；导入第三方包时，由 Core 登记同样的信息，不修改上游文件。该扩展缺失不影响普通导入、转换和使用。它不要求第三方包存在 `plugin.json`、README 或任何 NeuxAlly 特有文件。

此可选扩展的每个目标以现有 Runtime 基础身份为键，例如 `codex`、`claude`；值采用以下最小业务资料：

| 资料          | 含义                                                                    |
| ------------- | ----------------------------------------------------------------------- |
| `marketplace` | 目标 CLI 官方命令可接受的 marketplace 来源定位，格式由对应 adapter 解释 |
| `plugin`      | 该 marketplace 的准确原生插件定位，包含确定 marketplace 所需的信息      |
| `ref`         | 可选的 marketplace 固定 Git ref；不支持固定 ref 的来源不伪造支持        |
| `version`     | 可选的预期上游插件版本；用于结果校验，不假设原生命令支持按版本安装参数  |

第三方目录收录可只登记该关联和来源说明，不复制维护第三方技能。关联与其声明者、修订、来源摘要一起保存；后续关联更改不改写已经固定的目标结果。

同名插件不自动建立对应关系。关系由随包显式声明、受信收录资料或用户明确指定产生。安装前向用户可见的实际来源与目标能力组成必须能够查询，agent 不能凭名字相同默默替换。

### 4.2 选择顺序

1. 用户明确要求在当前目标安装某个精确原生来源时，采用该来源；其他目标仍可采用已声明关联。
2. 当前目标有明确关联且可由其原生机制安装时，使用该原生实现，并让目标 CLI 完成 marketplace 下载。
3. 没有对应实现时，优先使用包内已有的目标原生清单与完整内容。
4. 目标有原生插件接入能力时，由 adapter 生成目标原生清单及必要转换内容。
5. 目标没有原生插件接入能力时，只交付其支持的 Skill/MCP，并保留其余完整原始内容。

“原生插件接入能力”包含真实 CLI、版本、运行模式和 ACP 集成链路。平台名称、安装二进制存在或目标 JSON 校验成功均不足以证明原生加载可用。

命中原生关联后安装失败、被策略拒绝或缺少授权时返回真实结果，不把该错误当作不存在对应实现而自动换源。先记录已完成的结果，再允许在同一操作上重试。安装成功但未加载时不能返回当前可用。

### 4.3 固定实际内容

原生命令不支持直接安装任意版本时，可从已经解析并校验的固定来源构造本地原生 marketplace 或使用原生目录加载。仍无法保证指定版本时返回版本限制，不能只比较版本字符串后假称固定成功。

目标解析结果至少记录：资源版本、关联修订、目标 Runtime 配置身份、实际原生来源、上游版本、源码提交或可得的来源修订、完整内容摘要、adapter 修订、加载模式及组件集合。目标版本可以与原始来源不同，二者在展示与快照中分别表达。

缓存只保存确定性产物，密钥不进入内容摘要。相同源内容和相同转换规则应得到相同产物；账号、权限和配置变更另由配置修订及会话作用域处理。

## 5. 组件保留与转换

| 内容                 | 安装及转换要求                                                                       |
| -------------------- | ------------------------------------------------------------------------------------ |
| 标准元数据           | 映射到目标清单支持的字段；原清单保留；不编造作者、版本或许可                         |
| Skills               | 保留完整目录、相对依赖和 frontmatter；只有目标原生差异需要时改写派生内容，并记录差异 |
| MCP                  | 按传输、配置、环境与授权语义适配；`mcp.json` 与 `.mcp.json` 不仅是重命名关系         |
| Hooks                | 原定义和脚本完整保留；目标原生可直接解释时直接使用；有明确对应语义时转换事件与结构   |
| Agents               | 保留内容、资源和原生配置；正确区分技能内部 `agents/` 元数据与插件级 agent 定义       |
| Commands             | 保留 Markdown、脚本和资源；遵守目标发现及命名空间规则；不默认降为普通 Skill          |
| LSP                  | 保留定义和启动依赖；目标支持时原生加载；目标不支持时保留文件并报告未加载             |
| Apps / 托管连接      | 原样保留其平台配置；只交给对应平台解释；跨平台采用已声明原生实现或真实 MCP 映射      |
| 其他原生扩展         | 保留文件和原清单字段；目标认识的内容由目标处理；不以 NeuxAlly 白名单裁剪             |
| README / 许可 / 资产 | 保留原文、路径、摘要和来源，用于展示及追溯                                           |

需要转换的是实际语义差异：例如插件根目录变量、配置变量、MCP 传输值、清单组件路径和原生命名空间。不能全文搜索替换 `codex`、`claude` 或工具名，也不能把所有同名 hook 事件视为相同协议。

### 5.1 Skill 与 MCP 的最低转换要求

| 内容         | 具体规则                                                                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `SKILL.md`   | 保留标准 frontmatter、正文及相对资源；不以模型重新总结替换技能源文                                                                         |
| STDIO        | 保持 command、argv 顺序和 env；通用 `type: stdio` 按目标格式表达，不拼成 shell 字符串                                                      |
| HTTP         | 通用 `streamable-http` 对应目标原生 `http` 时转换该值；URL 和请求头保持其业务语义                                                          |
| SSE          | 目标与集成链路实际支持时交付，否则报告传输限制，不伪造 HTTP 等价                                                                           |
| `cwd`        | 目标有对应语义时直接映射；没有时复用现有无协议转换的 STDIO 启动机制，保持工作目录                                                          |
| 插件路径变量 | 在该字段允许替换的位置，将通用 `PLUGIN_ROOT` / `PLUGIN_DATA` 映射为 CC 的 `CLAUDE_PLUGIN_ROOT` / `CLAUDE_PLUGIN_DATA` 或目标真实支持的语义 |
| 用户配置变量 | 按目标原生配置机制解释；声明与值分开，保留 secret 语义，禁止把用户敏感值写入普通目标包                                                     |
| 原生认证配置 | 保留 OAuth、授权资源和其他原生认证声明，交由相应目标处理；未知认证字段不能从归一化结果消失                                                 |

MCP 的已知字段用于生成可交付配置，但原始 JSON 和额外原生字段同时保留。即使 NeuxAlly 的统一 MCP 结构暂时没有某个字段，目标原生可解释时仍应交付；能力无法迁移时报告具体字段与依赖限制。

一个输出包可以保留两个平台的原生清单。目标 adapter 只修改自己负责的清单及必须派生的文件；不需要改写的文件保持内容与相对位置。发生同路径改写时，原文件仍存在于不可变来源快照，产物记录对应转换及摘要。

外部 JSON 文件、内联定义和数组声明需要按各自原生顺序解释。对 CC 已有默认位置的追加、替换、合并和同名覆盖分别处理，不能为去重改变原生加载次序。

无法证明语义等价的 hook 或平台专有组件不编造替代实现，也不删除源内容。目标能解释的定义直接交付；目标未加载或运行失败时返回其实际结果，包含组件与可重试原因。没有原生插件能力的 CLI 只报告实际加载的 Skill/MCP 子集，不能称全部能力可用。

## 6. 导入、安装及发现

### 6.1 输入来源

支持现有本地目录和 ZIP，并增加来源解析入口：原生 marketplace 插件定位、Git 仓库加子目录及固定 ref、已安装原生插件身份。Git 子目录输入必须明确，不能把整个仓库根误判成一个插件。来源路径、清单与包内容分别校验，已有受管快照和内容摘要规则继续复用。

第三方完整原包的保存不受当前系统能展示多少组件限制。未知组件不阻止元数据登记；读取越界、无效清单、损坏归档等内容错误仍按原有边界报告。原生组件默认发现和安装行为由其 adapter 解释，不执行 README 中的任意命令作为安装协议。

### 6.2 对话操作

agent 能发现插件、查看实际来源与组成、检查目标适配、发起安装和查询真实结果。具体 CLI 参数及 Schema 在实施时进入现有 contract 目录，HTTP 契约从 OpenAPI 生成，不在本文重复建立一份接口声明。

受管安装上下文绑定本次 Execution、当前伙伴、资源归属和允许作用域。默认关联当前伙伴；访问更广安装范围需要已有明确请求依据。为使用全局配置的原生 CLI 下载或加载插件时，应选择可以满足该边界的原生作用域或会话加载机制。

agent 调用原生安装命令时，原生命令完成真正的下载。Core 通过结构化回执和同一目标的安装核对登记结果；不能只用 shell 退出码推断所有组件就绪。无法取得结构化结果时需要可验证的安装元数据，未识别结果保持未知。

### 6.3 软件外安装的发现

使用目标 CLI 官方的列表结果或其已确认安装元数据。发现时记录 CLI 配置身份、作用域、原生 ID、实际来源、版本、路径、启停和观察时间，必要内容复制为用于解析的不可变快照。

仅对当前选择或已配置的 CLI 范围进行核对，不扫描整台机器。触发点为安装动作结束、Core 启动后的已配置目标核对、目标切换、相关资源重新可见，以及原生安装元数据变化。文件监听合并事件，复用现有监听基础设施，不增加永久页面轮询。

软件外安装只产生外部观察关联，不自行生成所有伙伴的启用关系。通过软件当前对话发起并有明确操作证据的安装，可关联到该伙伴；缺少该上下文的安装只在资源库可见，用户选用后才进入伙伴范围。

软件关闭期间发生的变更在下次核对恢复。外部卸载令观察关联失效，但不删除仍被伙伴引用的内容快照或其他目标产物。原生路径内容变化要产生新的摘要记录，不能覆写旧执行引用。

### 6.4 幂等与并发

相同 request-id、相同输入返回同一安装操作；不同内容复用同键返回冲突。不同请求安装同一固定资源、同一目标与同一作用域时合并或串行核对，不重复下载和创建关系。

原生安装关联至少以 CLI 配置身份、作用域和原生插件身份区分；同一安装可以被多个伙伴引用。文件准备后原子发布到受管产物位置，失败暂存可清理，不出现被执行读取的半包。清理受内容引用和活跃执行占用约束。

外部效果与数据库登记之间保留可恢复记录。原生安装成功后 Core 中断，重启应先检查已存在安装再补登记。缺失回执不自动执行第二次安装，也不移除已经安装成功的内容。

## 7. 结果与生效边界

| 事实                | 可接受证据                                   | 不代表什么               |
| ------------------- | -------------------------------------------- | ------------------------ |
| 已保存              | 完整快照及摘要核对成功                       | 不代表原生安装完成       |
| 已安装              | 原生回执与安装身份核对，或已完成兼容资源准备 | 不代表当前会话已加载     |
| 已加载              | 原生组件清单、会话加载回执或可观测加载证据   | 不代表账号与业务操作成功 |
| 部分加载            | 实际加载组件与未加载组件分别列明             | 不代表完整原生能力       |
| 等待授权 / 原生确认 | 实际提供者或原生信任机制返回等待             | 不代表安装失败或可以绕过 |
| 运行失败            | 真实目标、组件和错误证据                     | 不自动删除原包或更换来源 |

安装结果需要提供资源身份、伙伴安装、目标、实际来源和版本、交付方式、阶段与阻塞原因；不包含凭据。用户普通界面使用中文业务文案，原生诊断可在详情中查看。

变更发生在活跃会话期间时，当前执行使用已经冻结的旧快照。可可靠重载的目标在安全边界自动加载；其他目标下一轮前自动重建并按现有规则续接。不得要求用户重复安装，也不得在安装过程中无提示中断正在执行的工作。

普通已授权原生使用遵循目标 CLI 的组件和信任机制。受限执行入口另行核对交付包是否满足目录、工具、账号和连接器范围；无法约束时拒绝该次整包交付，不能借原生插件绕开白名单。

## 8. README 预览与完整阅读

### 8.1 内容来源

说明必须绑定插件版本和完整内容摘要。目录预览使用该目录解析版本的 README；已安装详情使用所选来源版本，当前目标采用另一原生实现时显示该实现的来源与版本，正文读取同一实现的 README。不能用不同版本的生成说明覆盖原文。

解析顺序是根 `README.md`，再是 `readme.md`；文件不存在才回退标准长描述或短描述。空 README 显示无正文并提供现有短描述，不捏造章节。使用者主动查看某个历史版本时不自动切换安装版本。

### 8.2 预览

保留现有详情说明与元数据的容器布局。说明区默认采用约十二行正文的最大高度预算，按渲染结果裁切而不是截断 Markdown 源码；标题、列表、表格、代码块不产生残缺 Markdown。预算为设计作者建议，实施复用语义排版与空间变量。

只有内容实际溢出时，在说明下方显示“查看完整内容”。短正文直接完整展示，不保留无意义的展开按钮。容器宽度、主题、内容或字体布局变化后重新判断溢出，监听随卸载释放。

### 8.3 弹窗

点击后打开共享 Dialog，标题为插件名称及“说明”，正文以共享静态 Markdown 组件展示。弹窗使用现有 `size="xl"` 与适用的滚动布局，标题和关闭操作保持可见，正文独立滚动，不影响背景详情位置。

支持键盘进入、Escape 关闭与焦点返回触发按钮。加载、错误和重试只替换正文区，背景与弹窗标题保持挂载；版本切换和关闭取消无效请求，迟到响应不能覆盖另一个版本的正文。

“完整”表示读取范围内完整原文，不是截取后的字符串。内置正文读取上限从现有图标限制中分离，作者建议为 1 MiB；超过上限时明确告知无法内置阅读，并提供经过范围校验的原始文件查看入口。本机文件通过现有文件能力打开；远程来源可提供固定 ref 的原文件链接，由用户主动打开。原始快照保持完整，不能回退一个截断正文并称其完整。

### 8.4 Markdown 与资源

正文遵守共享 Markdown 规则：拒绝原始 HTML 执行，代码仅展示和复制，不自动加载远程图片。相对链接只在该固定版本的受管范围或已核验上游路径中解析，目录穿越和包外文件访问拒绝；不能将来源包的本机绝对路径交给任意外链打开。

概要列表只返回展示所需的摘要和 README 可读状态。完整正文按用户阅读动作获取，Query Key 包含资源、版本及实际来源身份；原生安装更新和资源事件只失效受影响内容。完整正文不复制进入第二套全局状态，也不为弹窗新建订阅通道。

## 9. 权限、所有权与卸载

保留现有共享账号、配置修订、提供者租约及执行内容占用约束。重复安装不重置既有启停和配置；切换 CLI 不复制一份账号或无依据地搬运另一产品的托管连接身份。

卸载当前伙伴只移除其关系与引用。最后一个应用引用消失且无执行占用后，才清理应用拥有的目标安装或缓存。外部原生安装默认保留；用户明确要求对指定原生作用域卸载时才调用原生命令。发现失败不等同于确认卸载，未知状态不能触发破坏性清理。

原生关联的源包和生成产物不能同时重复挂载其 Skill 或 MCP。调用权限继续使用稳定资源与组件身份，原生工具名和命名空间的变化由映射记录解释，不能通过任意改名绕过授权。

## 11. 实现者可自行决定的事项

保持上述行为的前提下，实现者决定内部文件拆分、最小表与索引、缓存目录命名和事件载荷的最小结构。数据库仍遵守单表查询与有界关联补齐规则，外部操作不进入数据库事务。

最终 HTTP 与 CLI Schema 通过现有生成及能力发现机制维护；本 Spec 不建立第二份参数表。新增配置或协议必须有真实调用需求，不能为尚未承诺的在线市场、账号体系或升级 UI 预建框架。
