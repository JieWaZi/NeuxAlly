# 插件 v2 Spec：标准映射、原生交付与验收

> 状态：v2 实现进入最终集成验收。本文规定设计要求，实际实现及未覆盖范围见 [验收记录](../plans/2026-10-19-plugin-v2-acceptance.md)，不将全部设计条目视为已完成。
> 意图、当前代码与职责见 [插件 v2 设计](2026-10-19-plugin-v2-design.md)。本文不是新的插件文件格式或 JSON Schema。

## 1. 采用的官方规范

规范依据核对日期为 2026-10-19。下列官方文档可能继续更新，adapter 实施时需同时记录实际 CLI 版本与支持的语义。

| 范围           | 权威来源                                                                                                           | 本系统采用方式                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------ | -------------------------------------------- |
| 通用清单       | [Agent Plugins 1.0.0 Schema](https://agent-plugins.org/schemas/1.0.0/plugin.schema.json)                           | 通用格式导入与校验，不新增必填顶层字段       |
| 通用 MCP       | [MCP Schema](https://agent-plugins.org/schemas/1.0.0/mcp.schema.json)                                              | 按传输和字段语义转换，不只修改文件名         |
| OpenAI 打包    | [Package your plugin](https://developers.openai.com/plugins/build/plugins)                                         | 通用根清单及 `com.openai` 扩展；接受兼容布局 |
| Codex 原生安装 | [CLI 插件命令](https://learn.chatgpt.com/docs/developer-commands?surface=cli)                                      | 按实际版本准备受管原生目录并核对会话加载结果 |
| CC 清单        | [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)                                     | 保留字段、默认发现及替换或合并语义           |
| CC 组件        | [Plugin components](https://code.claude.com/docs/en/plugins/components)                                            | 原生组件由 CC 执行，不实现第二套解释器       |
| CC marketplace | [Create a marketplace](https://code.claude.com/docs/en/plugin-marketplaces)                                        | 使用官方目录格式和来源定位                   |
| CC 安装与加载  | [Plugin commands](https://code.claude.com/docs/en/plugins/cli-reference)                                           | 受管会话目录加载，准确登记作用域             |
| 实际 OpenAI 包 | [openai/plugins 固定提交](https://github.com/openai/plugins/tree/0722921d5542fc593105c27bd52630babd8b8c2a/plugins) | 作为第三方来源和兼容样例，逐包保留声明       |

通用清单的 Schema 要求 `$schema` 与 `name`，其余标准属性包括 `version`、`description`、`author`、`homepage`、`repository`、`license`、`keywords` 和 `extensions`。根级别不添加 `allyPluginVersion`、自定义组件列表或新的格式标识。`extensions` 使用规范允许的命名空间，原生清单仍遵循各自规范。

自有插件与统一入口采用 Codex 标准：`.codex-plugin/plugin.json`、按需存在的 `skills/`、`.mcp.json` 及其他原生组件。NeuxAlly 专属引用与授权接入放在 `.neuxally/` 附加目录，不向官方清单增加新的私有必填字段。外部通用格式与 Claude 原生格式继续按原样收录和导入，不能强制转成 Codex 格式才允许登记。

授权额外依据 [OpenAI MCP 认证](https://developers.openai.com/plugins/build/auth)、[MCP Authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)、[MCP URL Elicitation](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation)、[CC MCP 认证](https://code.claude.com/docs/en/mcp) 与 [RFC 8628 设备授权](https://www.rfc-editor.org/rfc/rfc8628)。优先解释这些既有声明和协议；非标准 CLI 授权桥接明确属于可选业务扩展。

## 2. 标准目录与识别

| 内容     | 通用 Agent Plugins                 | Codex 兼容包                                  | Claude Code 原生包                           |
| -------- | ---------------------------------- | --------------------------------------------- | -------------------------------------------- |
| 主清单   | 根 `plugin.json`                   | `.codex-plugin/plugin.json`                   | `.claude-plugin/plugin.json`                 |
| 技能     | 根 `skills/`                       | 默认 `skills/` 及原生声明                     | 默认 `skills/` 及原生声明                    |
| MCP      | 根 `mcp.json`                      | 默认 `.mcp.json` 及原生声明                   | 默认 `.mcp.json` 及原生声明                  |
| 平台配置 | `extensions.com.openai` 等命名空间 | 兼容清单与配套文件                            | CC 清单与配套文件                            |
| 说明     | 插件根 README                      | 插件根 README                                 | 插件根 README                                |
| 其他组件 | 按扩展声明保留                     | 保留 apps、hooks、agents、commands 等实际内容 | 保留 hooks、agents、commands、LSP 等实际内容 |

目录与包文件必须保持完整相对结构，不只复制 `SKILL.md`。发布包不含 Git 工作目录，但包含脚本、引用资料、资产和必要可执行文件的执行位。

根通用清单存在时，它是通用身份和标准组件依据；目标平台配置分别读取。`extensions.com.openai` 为对象时，整体优先于 Codex 兼容 overlay，不对两个对象逐字段补齐。没有该对象时才采用兼容 overlay。只有原生清单时直接按原生格式导入，不先生成通用清单。

同时存在两个原生清单且没有根通用清单时，显式来源格式决定本次导入视图；来源没有指定时先选择本次目标 CLI 的清单，仍不能确定时要求选择格式。完整包只保存一份，两个原生清单都保留，不拼接成一份混合清单。

CC 的默认目录合并规则不能统一处理成“所有目录相加”。以当前官方清单为准：`skills` 追加默认发现；`commands`、`agents`、`outputStyles` 等声明可替换默认发现；hooks 和 MCP 等具有各自合并与覆盖规则。parser 与转换测试需要覆盖这些差异。CC 允许无清单的标准组件目录由原生机制识别；通过该机制发现的包可登记，但无法推导的元数据保持缺省，不伪造清单或版本。

### 2.1 自有插件的 Codex 标准示例

以下用虚构插件展示自有能力包，不定义新的包格式。`skills/issue-review/SKILL.md` 及其资源直接采用原生技能目录约定。

`.codex-plugin/plugin.json`：

```json
{
  "name": "issue-helper",
  "version": "1.0.0",
  "description": "检索问题并辅助整理处理建议",
  "skills": "./skills/",
  "mcpServers": "./.mcp.json"
}
```

根 `.mcp.json`：

```json
{
  "mcpServers": {
    "issues": {
      "type": "http",
      "url": "https://example.com/mcp"
    }
  }
}
```

Codex 直接使用该标准包。需要在 CC 使用自有内容时，由 adapter 生成 `.claude-plugin/plugin.json` 并转换确有差异的字段；不需要改写的 MCP、README、技能正文和其他文件保持原样。通用 Agent Plugins 格式仍是导入支持格式，其 `streamable-http` 等字段按前述标准解释，不混入本例的 Codex 清单。

### 2.2 三类仓库目录与统一安装身份

官方插件在源码仓库以固定来源声明及完整性锁收录，发布时通过 HTTP 获取完整上游包并生成安装 ZIP；不长期维护上游源码副本。以下完整原生文件结构描述发布产物，源码仓库对应原生目录只保存来源资料。逻辑入口及自有内容继续使用标准 Codex 包结构。插件清单的 `description` 说明业务能力，原生选择策略属于集成文档与声明。

发布结构以 GitHub 为例示意如下；固定来源收录、原生加载与真实账号业务验证分别核对：

```text
NeuAally-Plugins/
  codex-plugins/
    github/
      .codex-plugin/plugin.json
      ...原生内容
  claude-plugins/
    github/
      .claude-plugin/plugin.json
      ...原生内容
  neuxally-plugin/
    github/
      .codex-plugin/plugin.json
      README.md
      .neuxally/integration.json
    feishu-office/
      .codex-plugin/plugin.json
      skills/
      README.md
      .neuxally/integration.json
      .neuxally/auth/
```

`codex-plugins/` 与 `claude-plugins/` 收集完整原生包，保留其原始组件、作者和许可。`neuxally-plugin/` 是软件统一展示及安装的入口，既允许仅维护原生引用，也允许包含自己的实现。同一原生包由多个入口引用时不复制一份业务实现，软件可以共享同一个固定内容快照。

`neuxally-plugin/github/` 可以只有 Codex 标准元数据、说明与引用，用户安装的是这个入口。伙伴关系固定入口版本，目标交付另行记录实际 Codex 或 Claude 来源版本。原生 CLI 安装的是真正的能力包，不是等待它理解 NeuxAlly 引用的空壳。

`neuxally-plugin/feishu-office/` 按用户确认归自有插件：当前没有对应原生引用时使用自己维护的能力。自有内容按 Codex 规范编写，CC 交付由 adapter 转换；不单独复制维护一份 CC 飞书实现。包内来自官方的 CLI、技能与资源仍保留上游出处，不将“自有插件集成”描述为底层全部代码自研。

该目录约定只适用于自行维护的收录仓库。用户导入单个原生包，不需要先将它放进这些分类目录。

### 2.3 NeuxAlly 可选附加目录

`skills/`、`.mcp.json` 和其他组件按插件实际内容存在，不是统一入口的必填项。纯引用入口没有自有能力时，不伪造空 Skill 或 MCP；它在目标是否可用取决于引用能否解析。

`.neuxally/integration.json` 只记录本软件专属的 `nativePlugins`、`authentication` 等附加集成信息。插件身份、版本、作者、README、技能和 MCP 仍只有标准包中的一份权威来源；附加文件不是第二份插件清单。授权桥接路径相对于插件根解释，例如 `./.neuxally/auth/authorize`。

第三方标准插件没有 `.neuxally/` 时直接按原生规范导入，附加目录缺失本身不能导致包无效。增加该目录不改变官方清单的校验结果；移除它只移除 NeuxAlly 专属辅助信息，不承诺所有账号依赖仍已满足。原生 CLI 可忽略附加文件，实际授权仍需它自身的机制或 adapter 交付，不能假设它会执行 NeuxAlly 的桥接。

现有 v1 包中的 `extensions.com.ally` 按现有约定保持可读；本轮不改写已发布包或增加历史迁移。新增 v2 专属声明以附加目录为入口，同类信息不同时维护两份。遇到附加文件和旧扩展的重复或冲突声明时返回明确诊断，不静默合并；官方平台扩展继续遵循自身优先级。

## 3. 用于软件展示的标准字段

下表的 OpenAI `interface` 表示选定的 `extensions.com.openai.interface`，或符合上一节优先级的兼容清单 `interface`。CC 字段依据其原生清单；仅服务目录展示的字段，不因此成为运行依赖。

| 系统展示       | 通用 / OpenAI 字段                               | CC 字段或来源                        | 展示规则                                                  |
| -------------- | ------------------------------------------------ | ------------------------------------ | --------------------------------------------------------- |
| 标题           | `interface.displayName`，回退 `name`             | `displayName`，回退 `name`           | 用户明确设置的本机展示别名优先；保留原始名称              |
| 列表简介       | `interface.shortDescription`，回退 `description` | `description`                        | 展示原文，不由模型改写成新的权威说明                      |
| 说明正文       | 根 `README.md`，兼容 `readme.md`                 | 相同                                 | README 优先；缺失才回退 `longDescription` / `description` |
| 完整说明弹窗   | 同一来源版本 README                              | 相同                                 | 显示完整 Markdown，不把长描述冒充 README                  |
| 作者           | `author.name/url/email`                          | `author.name/url/email`              | 保留实际作者，不用收录方覆盖                              |
| 展示开发者     | `interface.developerName`，回退作者              | 作者；原生目录可提供展示资料         | 与第三方作者、适配维护者可分别表达                        |
| 版本           | `version`                                        | `version`                            | 目标实现显示自己的实际版本；缺失时明确采用内容摘要标识    |
| 仓库           | `repository`                                     | `repository`                         | 这是作者声明，实际下载来源由回执另列                      |
| 官网           | `interface.websiteURL`，回退 `homepage`          | `homepage`                           | 仅合法 HTTP/HTTPS 链接                                    |
| 文档入口       | README 及清单公开链接                            | `documentationUrl`、README           | 不作为清单解析或安装指令来源                              |
| 许可           | `license` 与随包许可文件                         | 相同                                 | 逐包保留，不替换为主应用许可                              |
| 分类           | `interface.category` 或原生目录分类              | 原生目录分类                         | 无值时不推断新的分类                                      |
| 标签           | `keywords`                                       | `keywords`                           | 缺失保持为空                                              |
| 图标           | `interface.logo` / `composerIcon`                | `icon` 或目录资产                    | 按主题选择可用资产，沿用受管资产校验；失败回退默认图标    |
| 暗色图标       | 兼容包中实际声明的 `logoDark` 等展示扩展         | 原生目录资产                         | 字段存在时读取，保留其来源，不宣称所有格式均必填          |
| 截图与品牌色   | `interface.screenshots/brandColor`               | 原生目录展示资料                     | 可选资料；是否展示由当前页面需要决定                      |
| 隐私与条款     | `interface.privacyPolicyURL/termsOfServiceURL`   | `privacyPolicyUrl/termsOfServiceUrl` | 原生键的大小写分别解释                                    |
| 建议提示       | `interface.defaultPrompt`                        | 原生目录提供时读取                   | 仅用户主动选择后形成输入，不自动执行                      |
| 能力           | 实际 skills、MCP 与完整原生组件索引              | 相同                                 | 展示真实组成，不以 `interface.capabilities` 代替组件事实  |
| 所需配置       | 原生配置声明与现有授权绑定                       | `userConfig` 等                      | 敏感值不回显；声明不等于已配置                            |
| 来源及安装状态 | 来源解析与原生安装回执                           | 相同                                 | 不能从 README、“已下载”或仓库 URL 推断已安装              |

包中未知字段和展示扩展完整保留，但不自动变成系统开关、权限或命令。共享配置及伙伴关系不写回第三方清单。

默认插件库的名称、简介和介绍读取 `neuxally-plugin/` 入口元数据与 README；查看实际实现或执行详情时读取所选原生包或自有内容的对应版本，并显示真实来源。入口维护者与原生作者、入口版本与原生版本分别表达，不能用统一入口元数据覆盖第三方署名或实际执行版本。包内能力清单来自当前目标解析结果，不要求在入口中重新封装或抄写所有原生技能。

## 4. 目标原生来源关联

### 4.1 这是业务关联，不是新插件标准

OpenAI 和 CC 没有共同定义“另一个生态中的对应插件”字段。该信息必须清楚标注为 NeuxAlly 维护的业务关联，不能包装成官方通用字段。

统一入口在 `.neuxally/integration.json` 的 `nativePlugins` 中携带原生关联；导入第三方包时，由 Core 登记同样的信息，不修改上游文件。该附加文件缺失不影响普通原生导入；自有能力也可以不声明原生关联。它不要求第三方包存在根 `plugin.json`、README 或任何 NeuxAlly 特有文件。

`nativePlugins` 的每个目标以现有 Runtime 基础身份为键，例如 `codex`、`claude`；值采用以下最小业务资料：

同仓库收录优先使用 `path`，相对于经过核验的 Git 来源仓库根目录解析，不是相对于入口目录或本机工作目录。它只允许定位对应收录树中的包，禁止绝对路径、`..` 或文件系统越界。解析器先在固定 Git 快照中解析引用，再将被引用包登记为独立内容快照；包内组件路径校验仍限制在各自包根内。

例如统一入口 `neuxally-plugin/github/.neuxally/integration.json` 可以声明：

```json
{
  "nativePlugins": {
    "codex": { "path": "codex-plugins/github" },
    "claude": { "path": "claude-plugins/github" }
  }
}
```

每个目标选择仓库 `path` 或外部 marketplace 定位之一，不混合解释。外部定位沿用以下资料；独立 ZIP 缺少来源仓库上下文而声明仓库路径时，应提供明确的来源解析错误，不能将路径解释为用户机器上的同名目录。

| 资料          | 含义                                                                    |
| ------------- | ----------------------------------------------------------------------- |
| `marketplace` | 目标 CLI 官方命令可接受的 marketplace 来源定位，格式由对应 adapter 解释 |
| `plugin`      | 该 marketplace 的准确原生插件定位，包含确定 marketplace 所需的信息      |
| `ref`         | 可选的 marketplace 固定 Git ref；不支持固定 ref 的来源不伪造支持        |
| `version`     | 可选的预期上游插件版本；用于结果校验，不假设原生命令支持按版本安装参数  |

第三方内容收集后，统一入口只登记关联和来源说明，不复制维护第三方技能。关联与其声明者、修订、仓库上下文、来源摘要一起保存；同仓库路径固定在入口所属的已解析提交中，不跟随远端 HEAD 漂移。后续关联更改不改写已经固定的目标结果。

同名插件不自动建立对应关系。关系由随包显式声明、受信收录资料或用户明确指定产生。安装前向用户可见的实际来源与目标能力组成必须能够查询，agent 不能凭名字相同默默替换。

### 4.2 选择顺序

1. 普通安装先固定 `neuxally-plugin/` 入口及伙伴关系；用户显式指定原生来源时按其明确请求登记，不凭名称自动归并。
2. 当前目标有明确原生引用时，解析并使用该原生包；同仓库包来自固定收录快照，外部 marketplace 来源经 HTTP/API 获取并固定内容，不能调用用户全局安装命令。
3. 当前目标没有原生引用时，使用统一入口自身的能力内容。没有引用且自有内容也为空时，明确返回该目标无实现，不自动编造或下载未声明替代品。
4. 选定内容后，目标有原生插件接入能力则原生交付：Codex 格式自有包在 Codex 直接使用，在 CC 由 adapter 做必要转换。
5. 选定内容后，目标没有原生插件接入能力则交付其支持的 Skill/MCP，并保留其余完整源内容，报告实际加载子集。

“原生插件接入能力”包含真实 CLI、版本、运行模式和 ACP 集成链路。平台名称、安装二进制存在或目标 JSON 校验成功均不足以证明原生加载可用。

命中原生关联后安装失败、被策略拒绝或缺少授权时返回真实结果，不把该错误当作不存在对应实现而自动换源。先记录已完成的结果，再允许在同一操作上重试。安装成功但未加载时不能返回当前可用。

### 4.3 固定实际内容

原生命令不支持直接安装任意版本时，可从已经解析并校验的固定来源构造本地原生 marketplace 或使用原生目录加载。仍无法保证指定版本时返回版本限制，不能只比较版本字符串后假称固定成功。

目标解析结果至少记录：资源版本、关联修订、目标 Runtime 配置身份、实际原生来源、上游版本、源码提交或可得的来源修订、完整内容摘要、adapter 修订、加载模式及组件集合。目标版本可以与原始来源不同，二者在展示与快照中分别表达。

缓存只保存确定性产物，密钥不进入内容摘要。相同源内容和相同转换规则应得到相同产物；账号、权限和配置变更另由配置修订及会话作用域处理。

统一入口版本的快照同时固定来源仓库上下文。只更新收录树、未修改入口文件时，已安装入口仍按其原提交解析原生包；不能用当前仓库 HEAD 重新解释旧入口。发布者希望同一逻辑插件采用新的原生内容时，应发布新的入口版本并固定新的引用结果。相同入口版本解析出不同原生内容时返回版本冲突，不因入口自身文件摘要相同而覆盖目标来源。

### 4.4 仓库维护、HTTP 查询与分发

源码维护入口为 [JieWaZi/NeuAally-Plugins](https://github.com/JieWaZi/NeuAally-Plugins)，其标准 OpenAI 索引为 [.agents/plugins/marketplace.json](https://github.com/JieWaZi/NeuAally-Plugins/blob/main/.agents/plugins/marketplace.json)。已恢复的飞书和 GitHub 包是现有应用集成基线；目录发布与 v2 功能验证分别表达。

来源列表可以包含多个标准 marketplace。OpenAI 既有包可以通过 [openai-curated 索引](https://github.com/openai/plugins/blob/0722921d5542fc593105c27bd52630babd8b8c2a/.agents/plugins/marketplace.json) 取得准确定位，再按固定来源收集到对应目录；CC 来源使用其标准 `.claude-plugin/marketplace.json`。发布工具生成 `schemaVersion: 2` 的 HTTP `catalog.json`，它是目录传输描述，不改变标准插件格式。

目标仓库分别维护软件入口索引与原生 CLI 索引。软件入口通过 HTTP `catalog.json` 只列出 `neuxally-plugin/`；每项携带 `key/sourceCommit/archiveURL/archiveSHA256/packagePath/name/version/description/format`。默认地址为公开 Release 的 `releases/latest/download/catalog.json`，安装 URL 固定具体版本。原生 Codex 索引保留标准默认位置，只列出可直接交付的 Codex 收录包与自有完整包；CC 索引只列出真实存在的 CC 原生包。索引可由发布工具生成，不把引用型空壳发布成原生 CLI 已具有能力的包。

默认资源库中 GitHub 只出现一个统一入口，两个原生实现作为其来源和实际交付内容；原生目录的来源查看及显式导入可达，但不复制默认安装项和伙伴开关。

| 查询内容         | 权威来源                                        | 本地行为                                               |
| ---------------- | ----------------------------------------------- | ------------------------------------------------------ |
| 可发现插件       | 已配置来源提交中的标准 marketplace 索引         | 缓存目录身份、来源及清单摘要，按本地索引搜索与分页     |
| 当前目标可安装   | 对应原生来源、目标 CLI 版本、adapter 和依赖检查 | 返回原生复用、转换、Skill/MCP 或具体阻塞，不靠名称推断 |
| 已验证兼容       | 明确的来源摘要、目标版本、交付方式和验证记录    | 无证据时保持未验证，不把公开可下载等同于已支持         |
| 当前伙伴已安装   | 原有伙伴关系及固定版本                          | 与远端目录分别查询，不用全部目录条目替代安装关系       |
| 当前机器原生安装 | 原生 CLI 回执与观察关联                         | 按 CLI 配置身份、作用域和真实内容核对                  |

首次同步读取索引，按条目补齐必要清单与展示元数据；README 全文按需获取。同步状态记录来源 URL、已解析提交、读取结果、新鲜度和错误，搜索读取已提交缓存；单个来源失败不清空其他来源。不存在完整目录缓存时表示未同步或未知，不返回伪造的完整总数。

Git 用于维护者开发与发布，应用运行时只通过 HTTP/API 获取元数据和固定归档，不要求用户具有 git 可执行文件。GitHub API 的访问频率与故障由来源获取模块处理，不让每次前端搜索都访问远端。无论使用哪种传输，都核对精确仓库、子目录与版本，不信任清单自报的 repository 作为来源证明。

安装固定目录快照后，Core 通过 HTTP 下载带摘要的完整来源归档；归档包含逻辑入口与所需原生引用，解包根是引用解析根，`packagePath` 定位逻辑入口。目录与 ZIP 都从插件仓库获取，应用发行包不内置安装 ZIP。经过安全解包与内容校验后登记，再按当前 CLI 生成应用拥有的原生会话目录。安装旧目录条目时若原生来源已变化，不静默改装新版；应使用已固定内容或返回目录需要刷新。

刷新触发限定为启动后的有界同步、用户主动刷新和安装确有需要的补齐；失败保留可用缓存与陈旧状态。目录刷新和原生来源同步不改变已有伙伴版本，也不自动执行源仓库脚本。公开 Git 用于目录与内容，不存储 token、用户账号、授权验证码或正在进行的授权会话。

| Commands             | 保留 Markdown、脚本和资源；遵守目标发现及命名空间规则；不默认降为普通 Skill          |

| 其他原生扩展         | 保留文件和原清单字段；目标认识的内容由目标处理；不以 NeuxAlly 白名单裁剪             |
| README / 许可 / 资产 | 保留原文、路径、摘要和来源，用于展示及追溯                                           |

需要转换的是实际语义差异：例如插件根目录变量、配置变量、MCP 传输值、清单组件路径和原生命名空间。不能全文搜索替换 `codex`、`claude` 或工具名，也不能把所有同名 hook 事件视为相同协议。

### 5.1 Skill 与 MCP 的最低转换要求

| 内容         | 具体规则                                                                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `SKILL.md`   | 保留标准 frontmatter、正文及相对资源；不以模型重新总结替换技能源文                                                                         |
| STDIO        | 保持 command、argv 顺序和 env；通用 `type: stdio` 按目标格式表达，不拼成 shell 字符串                                                      |
| HTTP         | 通用 `streamable-http` 对应目标原生 `http` 时转换该值；URL 和请求头保持其业务语义                                                          |
| SSE          | 目标与集成链路实际支持时交付，否则报告传输限制，不伪造 HTTP 等价                                                                           |
| `cwd`        | 目标有对应语义时直接映射；没有时复用现有无协议转换的 STDIO 启动机制，保持工作目录                                                          |
| 插件路径变量 | 在该字段允许替换的位置，将通用 `PLUGIN_ROOT` / `PLUGIN_DATA` 映射为 CC 的 `CLAUDE_PLUGIN_ROOT` / `CLAUDE_PLUGIN_DATA` 或目标真实支持的语义 |
| 用户配置变量 | 按目标原生配置机制解释；声明与值分开，保留 secret 语义，禁止把用户敏感值写入普通目标包                                                     |
| 原生认证配置 | 保留 OAuth、授权资源和其他原生认证声明，交由相应目标处理；未知认证字段不能从归一化结果消失                                                 |

MCP 的已知字段用于生成可交付配置，但原始 JSON 和额外原生字段同时保留。即使 NeuxAlly 的统一 MCP 结构暂时没有某个字段，目标原生可解释时仍应交付；能力无法迁移时报告具体字段与依赖限制。

一个输出包可以保留两个平台的原生清单。目标 adapter 只修改自己负责的清单及必须派生的文件；不需要改写的文件保持内容与相对位置。发生同路径改写时，原文件仍存在于不可变来源快照，产物记录对应转换及摘要。

外部 JSON 文件、内联定义和数组声明需要按各自原生顺序解释。对 CC 已有默认位置的追加、替换、合并和同名覆盖分别处理，不能为去重改变原生加载次序。

无法证明语义等价的 hook 或平台专有组件不编造替代实现，也不删除源内容。目标能解释的定义直接交付；目标未加载或运行失败时返回其实际结果，包含组件与可重试原因。没有原生插件能力的 CLI 只报告实际加载的 Skill/MCP 子集，不能称全部能力可用。

## 6. 导入、安装及发现

### 6.1 输入来源

支持现有本地目录和 ZIP，并增加来源解析入口：原生 marketplace 插件定位、HTTP/API 来源加子目录及固定提交、已安装原生插件身份。来源子目录输入必须明确，不能把整个仓库根误判成一个插件。来源路径、清单与包内容分别校验，已有受管快照和内容摘要规则继续复用。

第三方完整原包的保存不受当前系统能展示多少组件限制。未知组件不阻止元数据登记；读取越界、无效清单、损坏归档等内容错误仍按原有边界报告。原生组件默认发现和安装行为由其 adapter 解释，不执行 README 中的任意命令作为安装协议。

### 6.2 对话操作

agent 能发现插件、查看实际来源与组成、检查目标适配、发起安装和查询真实结果。具体 CLI 参数及 Schema 在实施时进入现有 contract 目录，HTTP 契约从 OpenAPI 生成，不在本文重复建立一份接口声明。

受管安装上下文绑定本次 Execution、当前伙伴、资源归属和允许作用域。默认关联当前伙伴；访问更广安装范围需要已有明确请求依据。系统安装不修改用户 Codex/Claude 全局插件环境；实际加载使用应用拥有的会话目录和原生配置。

agent 通过 allycli 发起系统安装，与界面复用相同用例。Core 取得真实系统安装回执；原生会话加载另取目标组件证据，不能只用下载成功或 shell 退出码推断所有组件就绪。聊天指引不得要求 agent 直接执行 Codex/Claude 全局安装命令。

### 6.3 软件外安装的发现

使用目标 CLI 官方的列表结果或其已确认安装元数据。发现时记录 CLI 配置身份、作用域、原生 ID、实际来源、版本、路径、启停和观察时间，必要内容复制为用于解析的不可变快照。

仅对当前选择或已配置的 CLI 范围进行核对，不扫描整台机器。触发点为安装动作结束、Core 启动后的已配置目标核对、目标切换、相关资源重新可见，以及原生安装元数据变化。文件监听合并事件，复用现有监听基础设施，不增加永久页面轮询。

软件外安装只产生外部观察关联，不自行生成所有伙伴的启用关系。通过软件当前对话发起并有明确操作证据的安装，可关联到该伙伴；缺少该上下文的安装只在资源库可见，用户选用后才进入伙伴范围。

已收录原生包被发现时，根据准确来源与显式引用关系关联到统一入口，不额外生成第二个默认安装资源。没有匹配入口的外部包继续作为本地导入资源可见，不要求先发布或修改公共仓库；后续关联也不能覆盖已经固定的来源和版本。

软件关闭期间发生的变更在下次核对恢复。外部卸载令观察关联失效，但不删除仍被伙伴引用的内容快照或其他目标产物。原生路径内容变化要产生新的摘要记录，不能覆写旧执行引用。

### 6.4 幂等与并发

相同 request-id、相同输入返回同一安装操作；不同内容复用同键返回冲突。不同请求安装同一固定资源、同一目标与同一作用域时合并或串行核对，不重复下载和创建关系。

原生安装关联至少以 CLI 配置身份、作用域和原生插件身份区分；同一安装可以被多个伙伴引用。文件准备后原子发布到受管产物位置，失败暂存可清理，不出现被执行读取的半包。清理受内容引用和活跃执行占用约束。

外部效果与数据库登记之间保留可恢复记录。原生安装成功后 Core 中断，重启应先检查已存在安装再补登记。缺失回执不自动执行第二次安装，也不移除已经安装成功的内容。

## 7. 结果与生效边界

| 事实                | 可接受证据                                   | 不代表什么               |
| ------------------- | -------------------------------------------- | ------------------------ |
| 已保存              | 完整快照及摘要核对成功                       | 不代表原生安装完成       |
| 已安装              | 原生回执与安装身份核对，或已完成兼容资源准备 | 不代表当前会话已加载     |
| 已加载              | 原生组件清单、会话加载回执或可观测加载证据   | 不代表账号与业务操作成功 |
| 部分加载            | 实际加载组件与未加载组件分别列明             | 不代表完整原生能力       |
| 等待授权 / 原生确认 | 实际提供者或原生信任机制返回等待             | 不代表安装失败或可以绕过 |
| 运行失败            | 真实目标、组件和错误证据                     | 不自动删除原包或更换来源 |

安装结果需要提供资源身份、伙伴安装、目标、实际来源和版本、交付方式、阶段与阻塞原因；不包含凭据。用户普通界面使用中文业务文案，原生诊断可在详情中查看。

变更发生在活跃会话期间时，当前执行使用已经冻结的旧快照。可可靠重载的目标在安全边界自动加载；其他目标下一轮前自动重建并按现有规则续接。不得要求用户重复安装，也不得在安装过程中无提示中断正在执行的工作。

普通已授权原生使用遵循目标 CLI 的组件和信任机制。受限执行入口另行核对交付包是否满足目录、工具、账号和连接器范围；无法约束时拒绝该次整包交付，不能借原生插件绕开白名单。

### 7.1 插件声明驱动授权

新插件接入已支持授权策略时，不得要求向 NeuxAlly 新增提供者常量、供应商专用 Go 分支或前端组件。通用宿主负责协议与会话，供应商特殊流程归插件。声明来源按以下规则解释：

| 授权来源            | 声明 / 发现位置                                                  | 通用处理                                                       |
| ------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------- |
| 标准远程 MCP OAuth  | MCP 401 挑战、受保护资源与授权服务器元数据                       | 通用发现、客户端注册、PKCE、回调和凭据刷新                     |
| OpenAI MCP 认证扩展 | 服务级 `extensions.com.openai.auth`，或原生兼容认证定义          | 映射已有 none、oauth、mixed、api_key 语义；不误读到插件根清单  |
| CC OAuth 配置       | 原生 `.mcp.json` 中相应服务的 `oauth` 等字段                     | 由 CC adapter 保留或映射客户端与元数据配置                     |
| 原生 CLI 授权       | 原生插件与 CLI 机制                                              | CLI adapter 接收结构化动作与实际结果；没有证据则保持等待或未知 |
| 标准设备授权        | 插件声明的服务器、公开 client ID、scope 与 RFC 8628 参数         | 通用设备授权模块发起、等待并遵循 interval、slow_down 和到期    |
| 插件专用授权        | 可选 `.neuxally/integration.json` 的 `authentication` 及包内桥接 | 桥接封装上游差异，宿主只解释统一交互协议                       |

MCP 标准 OAuth 面向 HTTP 传输，不把 STDIO 的环境凭据当成需要发起同一 OAuth 流程。客户端注册或回调域名有上游要求时由声明及安装配置满足；插件清单不能替代服务方的应用注册。

选用原生引用后，授权依据实际原生包及其服务声明。统一入口自带的桥接服务于自有内容，或有明确组件绑定的共享授权，不自动覆盖被引用包的 OAuth 客户端、端点与账号身份。没有原生引用而使用自有内容的飞书办公，才按自有声明启动其授权桥接。

本次获取的 Agent Plugins 1.0.0 MCP 核心 Schema 对服务字段采用严格集合，而 OpenAI 文档另有服务级认证扩展。实现需要分别校验核心与目标扩展、保留原始平台字段并记录采用的规范版本，不能修改公共核心 Schema 或声称带扩展对象已通过不接纳扩展的原始 Schema。上游不一致通过明确 fixture 与诊断覆盖，不以删除认证字段解决。

### 7.2 静态能力与动态授权挑战

静态声明表达授权策略、组件目标、配置需求及桥接入口；动态会话表达本次 URL、二维码、用户验证码、期限和结果。清单不固化短期授权 URL、设备码或用户 token。

Core 向前端提供统一的会话身份、挑战身份、状态、可用动作与期限。前端只根据动作类型显示以下组件，不判断插件名称：

| 动作        | 本次挑战提供的资料       | 界面                           |
| ----------- | ------------------------ | ------------------------------ |
| `open-url`  | 实际授权 URL             | 打开授权页面与必要的复制入口   |
| `show-qr`   | 本流程允许扫码的内容     | 共用二维码渲染与刷新入口       |
| `copy-code` | 用户验证码               | 单独展示和复制，不拼进未知链接 |
| 等待        | 当前挑战、可得期限与说明 | 等待、取消和实际支持的刷新     |

标准设备授权的 `verification_uri_complete` 可用于跨设备二维码，仍保留规范要求的用户验证码和文字 URL。普通 PKCE 链接若回调到本机 loopback，不自动转换成手机扫码；只有该流程明确支持跨设备时才展示二维码。MCP URL elicitation 的用户接受或打开 URL 不等于授权完成，应等待协议完成通知并核对状态或重试原操作。

刷新生成新挑战身份，旧二维码到期或取消后立即失效；同一会话可以依次发出创建应用、用户授权等挑战。插件只能声明与更新自己的会话，不能通过复用挑战 ID 影响另一个插件。

### 7.3 非标准授权桥接

OpenAI、CC 与标准 MCP 没有共同定义任意 CLI 扫码程序的启动与结果协议。下述 `neuxally-auth/1` 是本轮实现的可选交互扩展；它不替代现有插件格式，也不要求普通标准 MCP 包实现。精确消息以 [桥接实现](../../../server/internal/plugins/commandbridge/bridge.go) 和插件仓库的接入文档为准。

插件在 `.neuxally/integration.json` 的 `authentication` 中选择 `strategy: plugin-command`，声明 `protocol: neuxally-auth/1`、`command` 与 `args`。入口固定在已安装的包及其依赖内；执行文件与参数分开传递，不把清单内容拼成 shell 命令。平台依赖与入口的选择由包声明和原有资产机制完成。

下例使用虚构插件说明 `.neuxally/integration.json`，属于 NeuxAlly 的可选扩展，不是 OpenAI 或 CC 的标准清单；它只补充授权入口，不重复标准身份字段：

```json
{
  "authentication": {
    "strategy": "plugin-command",
    "protocol": "neuxally-auth/1",
    "command": "./.neuxally/auth/authorize",
    "args": []
  }
}
```

桥接采用进程级 JSON-RPC 2.0 行消息：stdin 接收请求，stdout 只输出协议消息，stderr 仅输出经脱敏的诊断。Core 管理进程和会话，供应商 CLI 输出由插件侧桥接解释。允许方法为：

| 方法           | 职责                                                               |
| -------------- | ------------------------------------------------------------------ |
| `auth/start`   | 接收 Core 签发的会话身份、插件私有数据目录和所需范围，发起上游授权 |
| `auth/status`  | 从真实凭据与上游或官方 CLI 状态核对账号摘要、有效范围和可用性      |
| `auth/cancel`  | 取消该会话的上游工作，实际停止后回应；不能只隐藏 UI                |
| `auth/resolve` | 为本次获准执行及组件提供必要环境或请求头，沿现有私密配置通道交付   |
| `auth/logout`  | 清理该插件受管身份，遵守共享引用与活跃执行占用                     |

Core 请求携带请求身份与会话身份，响应对应原请求；插件通过 `auth/challenge` 与 `auth/state` 通知更新交互。挑战包含会话、唯一挑战 ID、动作集合及可得的到期时间；状态覆盖等待、已授权、到期、取消和失败。Core 统一序列化公共状态与错误，原始协议帧不进入聊天 transcript 或前端日志。

例如同一通用界面可以接收以下虚构挑战，只有本次动作资料变化，不需要增加“office-example 专用授权页”：

```json
{
  "jsonrpc": "2.0",
  "method": "auth/challenge",
  "params": {
    "sessionId": "auth-example",
    "challengeId": "challenge-example",
    "actions": [
      { "type": "open-url", "url": "https://auth.example.com/device" },
      {
        "type": "show-qr",
        "value": "https://auth.example.com/device?request=example"
      },
      { "type": "copy-code", "value": "EXAMPLE" }
    ]
  }
}
```

动作中的 URL、二维码内容和验证码是桥接对本次会话实际发出的临时资料。前端只显示 Core 已绑定会话的挑战；不能把这段示例中的静态值当作可用授权入口。

桥接的账号摘要和凭据分开。私有 profile 只能位于 Core 为该插件分配的数据目录或经隔离的凭据存储；`auth/resolve` 的秘密值只在受管后端通道使用，不进入普通回执、模型指令或索引。返回的环境和请求头仅绑定本轮允许的稳定组件与声明目标，不能改变已获准 MCP 地址、Runtime 程序或访问另一插件的私有身份。

同一插件的伙伴复用共享身份。不同插件不能仅凭自报的账号名称或 provider 字符串合并凭据，跨资源共享必须有已核验的身份服务及作用域关系。已有飞书/GitHub v1 专用实现向桥接演进时继续保留隔离 profile、钥匙串命名空间与最后引用清理证据。

### 7.4 授权生命周期

授权状态由 Core 持有并通过既有资源事件交付，前端不轮询供应商。设备授权所需轮询在协议模块或桥接内部，遵守服务器间隔、退避、到期及取消；Core 退出时取消并等待受管进程释放。

未声明官方到期时间的流程可以使用有界本机等待，但应区分本机等待期限与官方有效期。点击“完成”、扫码、浏览器关闭或进程退出码均不能独立证明授权成功；以实际 callback、协议结果和状态核对为准。

安装回执仅向 agent 返回等待授权的会话引用、账号摘要及最终结果。短期码、原始授权 URL 与二维码只在当前授权界面需要时交付，结束后清除。缺少宿主已支持策略或桥接版本时准确说明限制，不转而要求新增供应商专用前端分支。

## 8. README 预览与完整阅读

### 8.1 内容来源

说明必须绑定插件版本和完整内容摘要。默认目录预览与统一插件介绍使用入口版本的 README；查看当前目标实际实现时，显示该实现的来源、版本及 README。入口说明与原生说明分别标明来源，不将不同版本的生成说明覆盖原文；完整内容弹窗始终与当前说明区指向同一份正文。

解析顺序是根 `README.md`，再是 `readme.md`；文件不存在才回退标准长描述或短描述。空 README 显示无正文并提供现有短描述，不捏造章节。使用者主动查看某个历史版本时不自动切换安装版本。

### 8.2 预览

保留现有详情说明与元数据的容器布局。说明区默认采用约十二行正文的最大高度预算，按渲染结果裁切而不是截断 Markdown 源码；标题、列表、表格、代码块不产生残缺 Markdown。预算为设计作者建议，实施复用语义排版与空间变量。

只有内容实际溢出时，在说明下方显示“查看完整内容”。短正文直接完整展示，不保留无意义的展开按钮。容器宽度、主题、内容或字体布局变化后重新判断溢出，监听随卸载释放。

### 8.3 弹窗

点击后打开共享 Dialog，标题为插件名称及“说明”，正文以共享静态 Markdown 组件展示。弹窗使用现有 `size="xl"` 与适用的滚动布局，标题和关闭操作保持可见，正文独立滚动，不影响背景详情位置。

支持键盘进入、Escape 关闭与焦点返回触发按钮。加载、错误和重试只替换正文区，背景与弹窗标题保持挂载；版本切换和关闭取消无效请求，迟到响应不能覆盖另一个版本的正文。

“完整”表示读取范围内完整原文，不是截取后的字符串。内置正文读取上限从现有图标限制中分离，作者建议为 1 MiB；超过上限时明确告知无法内置阅读，并提供经过范围校验的原始文件查看入口。本机文件通过现有文件能力打开；远程来源可提供固定 ref 的原文件链接，由用户主动打开。原始快照保持完整，不能回退一个截断正文并称其完整。

### 8.4 Markdown 与资源

正文遵守共享 Markdown 规则：拒绝原始 HTML 执行，代码仅展示和复制，不自动加载远程图片。相对链接只在该固定版本的受管范围或已核验上游路径中解析，目录穿越和包外文件访问拒绝；不能将来源包的本机绝对路径交给任意外链打开。

概要列表只返回展示所需的摘要和 README 可读状态。完整正文按用户阅读动作获取，Query Key 包含资源、版本及实际来源身份；原生安装更新和资源事件只失效受影响内容。完整正文不复制进入第二套全局状态，也不为弹窗新建订阅通道。

## 9. 权限、所有权与卸载

保留现有共享账号、配置修订、提供者租约及执行内容占用约束。重复安装不重置既有启停和配置；切换 CLI 不复制一份账号或无依据地搬运另一产品的托管连接身份。

卸载当前伙伴只移除其关系与引用。最后一个应用引用消失且无执行占用后，才清理应用拥有的目标安装或缓存。外部原生安装默认保留；用户明确要求对指定原生作用域卸载时才调用原生命令。发现失败不等同于确认卸载，未知状态不能触发破坏性清理。

原生关联的源包和生成产物不能同时重复挂载其 Skill 或 MCP。调用权限继续使用稳定资源与组件身份，原生工具名和命名空间的变化由映射记录解释，不能通过任意改名绕过授权。
