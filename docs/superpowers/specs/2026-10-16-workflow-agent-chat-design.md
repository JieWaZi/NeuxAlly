# 聊天调用工作流 SPEC

## 目标和批准范围

用户在普通伙伴聊天中选择一个已保存工作流并描述任务。当前 Agent 通过现有 `allycli` 读取契约、自动填写输入、启动运行、持续等待，最后把总结和最终文件交付到原聊天。聊天中独立展示本次工作流调用，点击在右侧打开准确的运行过程。聊天与运行支持双向感知用户停止。

本 SPEC 固化[设计讨论](../../discussions/workflow-agent-chat-cn.md)中用户逐项确认的行为，以及用户明确要求通过现有 CLI 完成启动和等待的职责边界。用户已授权先编写 SPEC 和计划，再在独立 worktree 分支开发。尚未形成行为变更的细节由实施者依据本 SPEC 和仓库约定决定。

## 范围和约束

* 首版一条消息最多选择一个工作流；内部节点、多个 Agent 和子流程沿用既有工作流规则。
* 仅为普通伙伴聊天新增入口。团队对话和工作流创作／调整的发送契约保持既有行为，不显示无法传递的引用入口。
* 任务理解、参数组织、启动、重复等待和总结由 Agent 完成。应用不新增自动启动、参数推断或等待调度器，不为各工作流生成独立技能或连接器。
* 复用系统 `skills/ally`、`allycli`、现有工作流服务、消息日志、共享组件和统一资源事件；不新增前端永久轮询或业务连接。
* 每个真实运行只有一份权威状态；UI、聊天和工作看板读取原 Workflow 数据。
* 仅在独立 worktree 的功能分支修改并提交，不合并 main、不推送。保留原目录的讨论稿。
* 所有新增和修改 Go 结构体的全部字段具有中文注释；公开 API 字段使用简短业务标签。生成文件只运行生成命令更新。
* SQL 默认单表查询，既有关联通过索引条件和有界批量读取完成，不为展示字段新增 JOIN。
* 未获明确授权不打开、控制或截图运行中的应用或页面。自动化验收与真实模型、视觉验收分别报告。

## 用户流程

1. 聊天输入框补全列表提供工作流搜索，选择后形成类型化引用；同一草稿只能有一个工作流，选择另一个替换原引用。
2. 发送携带稳定定义 ID；只有已保存且有当前 Revision 的工作流可选。名称及用途用于展示，不根据自由文本猜测调用身份。
3. Agent 从实际契约读取不可变 Revision，自动组织输入，并把该 Revision 显式传给启动命令。任务意图、上下文、工作区查询和默认值足够时直接执行。
4. 只有必要业务信息确实无法确定时，通过聊天追问；不能因为必填字段尚未填写就要求用户重写已经说明的任务。
5. 启动回执确定本次 `runId`。Agent 对该运行调用有界 `wait` 或 `get`，未达终态继续等待，直到成功、失败或实际取消。
6. 最终内容经 Agent 总结进入原聊天；最终文件以真实会话文件进入消息。两种产出可同时交付。

示例：用户选择“五方代码评审”，发送“用这个工作流 review 本次改动”。Agent 使用当前获准项目和改动上下文组织审查任务。流程内五个 Agent 各自评审，当前 Agent 等待结束并汇总最终结果，无需用户再填写一份评审说明。

## 输入、权限与重试

* 聊天请求继续使用已有 `workflowIds`，聊天边界校验最多一个。工作流引用写入权威消息事实，刷新、队列发送和发送失败恢复后保持准确身份。
* 本次授权绑定真实聊天和 Execution，只允许所选定义及该聊天获准的运行。模型知道其他 ID 不构成权限。
* 当前聊天配置作为运行默认值，节点显式配置继续生效，但不得扩大调用者工作范围或权限。
* 输入文件沿用现有冻结和路径校验，普通字符串不推断为文件。
* 启动沿用稳定请求身份和原回执。响应不确定时先查原回执，不更换请求身份重跑。观察超时、断线和总结失败不构成重新执行授权。

## 等待、结果与停止

单次 `wait` 超时结束的是观察，并不改变运行状态。Skill 明确要求 Agent 继续等待同一运行，不能以“已启动”完成任务。`completed` 表示达到终态，成功、失败、取消仍看实际运行状态及原因。Core／Runtime 异常要显示真实中断边界，不伪装 Agent 仍在线。

| 事件 | 系统行为 |
| --- | --- |
| 运行成功 | 返回最终结果和声明文件信息，Agent 总结并交付 |
| 运行失败或总期限耗尽 | 保留失败原因，Agent 告知用户；可确认的部分结果标明未完整完成 |
| 聊天停止 | Core 关闭本次调用授权并传播取消，停止当前 Agent；执行项保留实际状态，不重新唤醒 Agent 回复 |
| 右侧停止 | 保存用户停止来源，进入正在停止；实际收敛后等待者得到用户主动停止原因，Agent 简短说明后结束任务 |
| 运行已经终态后停止 | 不改写已有成功、失败或取消结果 |
| 重复停止 | 幂等，不产生重复运行、重复副作用或错误的失败原因 |

取消传播由 Core 执行，不依赖被停止或撤销授权的 Agent。取消与接纳并发时，已关闭的调用授权不得在取消查询窗口之后创建遗漏的新运行；实现须覆盖这一竞态。用户停止后不自动重试或换方式继续同一任务。

## 消息与右侧过程

* 每次运行在所属助手消息中展示独立执行项，包含工作流名称、状态及查看过程入口；启动、查询和等待不堆叠为多个相同业务调用。
* 执行项以真实 `runId` 定位；刷新重放后仍能打开原运行，不打开当前最新运行或创作聊天。
* 右侧复用现有工作流画布、节点状态、详情、人工请求和运行停止能力；关闭标签、切换页面和窗口隐藏不取消业务。
* 通过已有统一事件按准确资源更新；运行成功与 Agent 正在总结分别表达，运行状态不被消息交付状态覆盖。
* 原运行查询失败、离线、已删除和陈旧数据在所属区域反馈，不显示虚假的成功或空运行。

## 文件交付

* 只从不可变输出 Schema 的 `format:file` 字段及已确认结果获取最终文件；普通字符串和任意模型路径不能进入交付。
* Core 校验文件归属及真实字节，复用 Chat 受管附件能力固化并保存来源身份；助手消息中的文件可直接打开、预览或下载。
* 同一 Run 和输出字段重复读取、重连或总结重试不重复附加文件。同名文件来自不同运行时各有稳定身份，不互相覆盖。
* 文件保存和消息登记之间有明确顺序及恢复机制。文件已存在但登记失败时重试登记，不重新执行工作流。
* 文件不存在或不可读时，如实展示交付失败，保留原运行终态。Agent 总结失败时保留已确认的文件和原结果。
* 中间节点产物留在右侧；失败／取消时只交付可确认的部分结果，不把所有节点文件自动发送到聊天。

## 责任和数据归属

| 所有者 | 职责 |
| --- | --- |
| Agent／Skill | 自动准备参数，调用现有 CLI，持续等待，理解真实失败／停止原因，总结和呈现最终交付 |
| Workflow | 原接纳、版本、运行、取消原因及最终产出；维护原运行与调用 Execution 的准确关联 |
| Chat／Execution | 原消息、引用快照、正式交付文件、调用展示事实和用户停止传播；授权终止后不能继续接纳 |
| 前端 | 输入引用和发送恢复，消息执行项，右侧运行过程，精确事件消费 |

运行关联复用既有 `consumerLeaseId` 事实及可索引的领域关联，不建立另一套运行生命周期。新增查询必须有界，不按历史消息逐个扫描整个工作流目录。展示和文件交付只接受服务端确认的关联，原生模型输出不能伪造受信调用。

## 实施者决定的细节

以下是实施者的工程选择，不代表用户另行指定了这些细节：

* 默认在已有 `/` 补全列表增加“工作流”分组并保留技能分组，使用类型化节点避免同名碰撞，不引入新的快捷字符。
* 通过 Chat 公开贡献槽与 app 装配复用 Workflow 的过程内容，不从 Chat 内部导入 Workflow 内部组件。
* 使用既有命令回执和权威日志保存可重放的调用引用；具体 Go 方法和附加字段在计划中确定，优先复用既有类型。
* 前端列表按已有游标分页查询，不将首屏结果当作全部工作流。

## 验收标准

1. 普通聊天能搜索并选择一个工作流；选择第二个替换，删除引用撤销选择；队列、发送失败恢复和刷新后身份一致。
2. 新建与续发请求均限制一个，未选择定义和其他聊天运行不可调用；选中但未保存的流程不可发送。
3. 实际 CLI 通过授权读取契约、带参数启动、持续等待同一个运行并得到内容结果；观察超时不取消或重跑。
4. 用户任务已经足够时 Agent 自动组织参数；只有真实信息缺失才追问。此项需要受控 Agent 行为验证，静态检查 Skill 文本不构成行为验收。
5. 消息执行项打开确切 Run 的右侧画布；刷新、状态更新、失败和已停止均准确，关闭面板不取消。
6. 两个入口停止和接纳竞态、重复停止、停止与终态并发均有自动化回归；右侧停止的查询结果明确标识用户停止。
7. 最终内容和文件混合交付成功，重复观察不重复附件；未声明文件、越界软链接、缺失文件和同名文件分别验证。
8. 助手消息在文件交付前后形成的不同顺序、登记失败重试及日志重放均得到同一可用交付引用。
9. 执行仓库要求的 `pnpm check`（含 Go vet、Go test、API 生成一致性及前端检查），必要时补充 race 与 SQL 查询计划验证；不修改检查豁免。
10. 报告独立审查结果、自动化证据，以及未获授权进行的真实桌面视觉或真实账号模型验收边界。
